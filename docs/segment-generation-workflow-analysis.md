# 分镜级生成控制 — 深度分析

> 用户提议: 结果页让用户为每个缺失素材的分镜选择"生成图片"或"生成视频"，  
> 先生成提示词让用户审核，再提交 RunningHub 生成，最后嵌入视频

---

## 一、这个想法好在哪

### 1.1 解决的真实问题

| 当前痛点 | 这个方案怎么解决 |
|------|------|
| 用户不知道 AI 会生成什么 | 先生成提示词 → 用户审核 → 再生成图片/视频 |
| 5段全生视频 = 25分钟 + ¥5 | 用户只对关键段选视频，其余用图片 |
| 批量生成的图片如果不好，全部重来 | 逐段确认，失败只影响一段 |
| "生成"按钮是黑箱，用户无参与感 | 分镜级选择 → 透明可控 |

### 1.2 与赛题要求的契合度

| 赛题要求 | 这个方案如何满足 |
|------|------|
| "人工可调" (8分) | 用户逐段选择生成方式 + 审核提示词 |
| "迁移过程可视化" (10分) | 每段展示 "生成策略 → 提示词 → 成品" 完整链路 |
| "AIGC 补全" (12分) | 明确展示哪些段用图片/视频补全及原因 |
| "人机协同" (15分) | 用户决策 + AI 执行的协同模式 |

## 二、需要解决的设计问题

### 2.1 时机问题: 必须先完成分析和评估

> "在进行这一整个流程之前必须得完成其他的结果分析和优化建议等"

**正确。** 这个流程应该在以下条件全部满足后才启动：

```
前置条件检查:
  ✅ 参考视频已分析 (VideoStructure 已生成)
  ✅ 产品信息已填写 (brief 已保存)  
  ✅ 脚本已生成 (FinalScript 已存在)
  ✅ 评分预测已完成 (predicted_scores 已计算)
  ✅ 缺口检测已完成 (gaps 已标记)
  ✅ 素材匹配已完成 (asset_matcher 已运行)
  ✅ 优化建议已生成 (weakest dimensions 已展示)
```

这些前置条件已经由 MigratePage → 生成脚本 → 进入 ResultPage 的流程保证了。

RENDER ALL 完成后，每段卡片自动展示状态：

### 2.3 状态管理: 每段的生成状态需要跟踪

```typescript
interface SegmentGenerationState {
  segmentId: string;
  mode: 'image' | 'video' | 'none';     // 用户选择
  promptText: string;                     // 生成的提示词
  promptApproved: boolean;                // 用户审核通过
  generationStatus: 'idle' | 'prompting' | 'prompt_ready' | 'generating' | 'completed' | 'failed';
  resultUrl?: string;                     // RunningHub 返回的 URL
  taskId?: string;                        // 异步任务 ID
}
```

## 三、技术可行性

### 3.1 后端需要的改动

| 改动 | 复杂度 | 说明 |
|------|:--:|------|
| 分镜级生成 API | 中 | `POST /api/v1/render/{id}/segment/{n}/generate` — 接受 mode(image/video) + approved_prompt |
| 提示词预览 API | 低 | `POST /api/v1/render/{id}/segment/{n}/preview-prompt` — 返回中英文提示词但不调用 RunningHub |
| 异步生成状态追踪 | 低 | 已有 `upgrade-to-video` 的 task_id 模式，可直接复用 |
| 逐段组装 | 低 | `_process_segments` 已支持逐段处理，只需按 mode 切换 Flux/WAN |

### 3.2 前端需要的改动

| 改动 | 复杂度 | 说明 |
|------|:--:|------|
| ReviewPanel 卡片扩展 | 中 | 每段增加 mode 选择器 + 提示词预览 + 状态指示 |
| 生成预估面板 | 低 | 成本和时间预估 |
| 逐段提交逻辑 | 中 | 点击提交 → 预览提示词 → 确认 → 异步轮询 → 更新状态 |

### 3.3 单一流程（不高多模式）

**不搞两个模式。** 只保留一条最高级的单一流程：

```
RENDER ALL（唯一入口）
  → 全部 Flux 图片（快，~1分钟/5段）
  → 视频渲染完成后：
     每段分镜卡片自动展示状态 + 智能建议
     用户可在任意时刻选择升级关键段为视频
```

也就是说，**把现有的 `UPGRADE TO VIDEO` 按钮强化**，不需要新增模式：

| 改前 | 改后 |
|------|------|
| 一个不起眼的小按钮 | 渲染完成后自动展开，含智能建议 + 成本预估 + 提示词预览 |
| 用户不知道有什么用 | 智能建议明确告诉用户：Hook/Product 段建议升级 |
| 点完不知道要等多久 | 显示预估时间（~4.5分钟/段）+ 后台异步，可切换页面 |

## 四、风险评估

| 风险 | 严重度 | 缓解 |
|------|:--:|------|
| 用户操作负担增加 | 中 | 保留 RENDER ALL 作为一键默认；精细模式是可选高级功能 |
| 逐段生成耗时更长（用户等待） | 低 | 后台异步生成，用户可以切换页面，完成后通知 |
| 提示词预览需要额外 LLM 调用 | 低 | 复用 AIVideoService.generate_prompt_only()，已有此方法 |
| RunningHub 并发限制 | 低 | 逐段提交自然控制并发，不会同时发起 5 个视频生成 |


## 七、结论

**单一流程，逐段升级。** 

流程设计:
1. RENDER ALL → 自动 Flux 生图（快） → 视频渲染完成
2. 每段卡片自动展示：🖼️已生成 + 💡智能建议 + [🎬升级为视频]
3. 用户点升级 → 预览提示词 → 后台异步生成 → 自动替换对应段

核心设计原则:
1. **先分析后生成** — 评分/缺口/建议全部完成后才启动
2. **图片是基线，视频是增强** — 先保证完整视频，再选择性提升
3. **逐段独立** — 每段状态互不干扰
4. **全异步** — 生成中可以切换页面，完成后通知
5. **不搞多模式** — 单一 RENDER ALL 入口，不给用户选择困难
