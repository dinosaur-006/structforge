## 1. 评分是真还是假？

### 结论：**评分是真实的规则量化计算，不是随机数**

`result_evaluator.py` 中的 `_evaluate()` 方法基于**可解释的爆款特征公式**计算五项维度得分，每一项都有具体的判定规则：

### 1.1 Hook 强度（hook_strength）

| 判定条件 | 分值 |
|---------|------|
| Hook 段是否为第一个分镜 | +20 |
| Hook 时长 ≤ 2s | +15，≤ 3s | +10 |
| Hook 段有素材覆盖 | +15 |
| 文案长度 > 20 字 | +15，> 10 字 | +5 |
| 文案含疑问句或反转词（"别划走""等等""居然"）| +15 |
| 文案含情感触发词（"炸裂""惊呆了""受不了"）| +10 |
| 文案含注意力打断词（"停""看"）| +10 |

### 1.2 产品首次露出时机（product_exposure_timing）

| 判定条件 | 分值 |
|---------|------|
| 产品首次出现 ≤ 5s | +30，≤ 8s | +15 |
| 产品段有素材覆盖 | +25 |
| 文案长度 > 20 字 | +15 |
| 文案将产品描述为"解决方案" | +15 |
| 产品段存在 | +15 |

### 1.3 卖点证明力（selling_point_proof）

| 判定条件 | 分值 |
|---------|------|
| 有 Proof 段 | +20 |
| 有素材覆盖 | +15 |
| 含具体数据（数字+单位，如"87单""降20"） | +20 |
| 含模糊数字 | +10 |
| 文案 > 40 字 | +15，> 20 字 | +5 |
| 含对比词（"vs""比""更"） | +15 |
| 含信任信号（"认证""检测""实测"） | +15 |

### 1.4 节奏紧凑度（pacing_compactness）

基于分镜时长方差和平均时长计算。时长变异大（有快有慢）= 加分。

### 1.5 CTA 转化号召力（cta_persuasiveness）

| 判定条件 | 分值 |
|---------|------|
| CTA 段为最后一个分镜 | +20 |
| 有素材覆盖 | +15 |
| 文案 > 30 字 | +15 |
| 含紧迫感词（"现在""立即""马上""仅剩"） | +15 |
| 含稀缺性词（"仅剩""限量""最后"） | +15 |
| 含零风险承诺（"不满意退""无条件退"） | +15 |
| 含具体行动指令（"点击""下单""购买"） | +15 |

## 2. 45→64 (+19) 的改进是真的吗？

### 结论：**这个改进是 LLM 根据审计指令定向优化的结果**

用户日志显示 LLM 生成的优化建议：

> "将产品首次露出时间从原27秒提前到第3秒，远低于平台高转化要求的5秒阈值"
> "把原仅露出品牌logo的无效CTA替换为带明确行动指令、稀缺库存提示、零风险承诺的高转化内容"

这两条直接对应了评分公式中的加分项：

| 维度 | 原脚本 | 优化后 | 公式中加分 |
|------|--------|--------|-----------|
| 产品露出 | 27s 才出现 | 10s → product_score +15 | ✅ 真实改进 |
| CTA 文案 | 仅品牌 logo | "直降20，仅剩87单，不满意退" → cta_score 多项加分 | ✅ 真实改进 |
| Proof 文案 | 未统计 | "你看这橙子爆汁的鲜活质感" → 含具体描述 | ✅ 可能改进 |

### 但是：评分公式存在结构性缺陷

1. **`visible` 字段始终为 True**——不去检查分镜是否真的有视频素材覆盖。所以即使所有分镜都是黑屏，素材覆盖率仍为 100%。

2. **纯文本分析**——"不满意退"三个字触发风险反转加分，"87单"触发数据加分。这是关键词匹配，不是语义理解。

3. **零视觉相关性**——评分完全不考虑视频画面质量。黑屏 + 好文案 = 高分。

## 3. 黑屏问题为什么还在？

### 根因：LLM 返回的脚本把所有分镜标记为 `source="original"`

当 LLM 成功生成脚本时（非 fallback），它在 JSON 中将 segments 的 `source` 设置为 `"original"`。这不是 fallback 脚本（`_build_fallback_script`）的逻辑——是 LLM 自身在 prompt 中看到的输出格式示例就是 `"source": "original"`。

**数据流追踪**：

```
LLM 返回:
  segments: [
    {id: "1", source: "original", asset_id: null},  ← LLM 自己写的 "original"
    ...
  ]

_auto-wrap → FinalScript 含 source="original", asset_id=None

compositor:
  1. asset_id=None → source_path=None → 进入 no-asset 分支
  2. segment.source = "original" ≠ "packaging" → 走 else → AI 提示词卡片路径
  3. 这段代码有 shot_used 未定义的 bug（已修复但用户需要重启）
```

**所以修复代码逻辑是正确的，但用户需要重启服务器让新代码生效。**

## 4. TTS 语速太慢导致截断

### 根因：TTS 合成固定速度，与分镜时长不匹配

`tts_engine.py` 的 `synthesize()` 使用固定 `speed` 参数，不根据分镜时长动态调整。当分镜只有 3 秒但字幕文案有 40 字时，语音无法在 3 秒内播完。

### 涉及代码

`compositor.py:334` — `tts.synthesize(full_script, full_tts_path, target_duration=total_dur)`

`tts_engine.py` — `synthesize()` 方法中 `speed` 参数是固定的 `self.settings.tts_speed`（默认 1.0），不根据 `target_duration` 计算所需加速比。

### 需要的修复（不写代码，仅说明）

TTS 合成前应计算所需语速：`required_speed = total_chars / (target_duration * chars_per_second_at_normal_speed)`，然后将此速度传给 TTS API。或在 FFmpeg 中用 `atempo` 滤镜调整已合成音频的速度以匹配分镜时长。
